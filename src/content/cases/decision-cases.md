## D02 为什么选 DeepSeek 而不是 GPT-4o

选 LLM 供应商是整个项目的根基。2026 年 6 月，GPT-4o 是行业标杆，Function Calling 最稳定，生态最完善——几乎所有 AI 教程都推荐它作为默认选择。但我在 EIA 的核心场景里算了一笔账，决定否决。

### 冲突

EIA 每次分析需要调用 5+ 次 LLM：Supervisor 路由决策 + 3 个领域 Agent 查数据 + Report 生成报告 + Reflection 质检。如果一个客户的日均分析量是 100 次，月调用量就是 15,000 次。在这种规模化场景下，模型单价的微小差异会被放大到不可接受。

AI 的建议是选 GPT-4o，理由是"行业标准、最稳定"。但这个建议没有算成本。

### 我的判断

我否决 GPT-4o 的核心理由不是"它不好"，而是"在这个场景和成本结构下，ROI 不成立"。具体三个维度：

**1. 成本差 15 倍**。我在 20 条离线评估集上做了对比测试：

| 维度 | DeepSeek-V4 | GPT-4o | Claude Sonnet 4 |
|------|:--:|:--:|:--:|
| SQL 生成准确率 | 85% | 88% | 87% |
| 中文报告流畅度 | ★★★★★ | ★★★☆☆ | ★★★★★ |
| 中文零售术语理解 | 好（"客单价"准确） | 中（偏英文直译） | 好 |
| 单次分析成本 | **¥0.04** | ¥0.60 | ¥0.80 |
| 月成本（100 次/天） | **¥120** | ¥1,800 | ¥2,400 |
| Function Calling | 偶尔超时 | 稳定 | 稳定 |

GPT-4o 的 SQL 准确率仅高 3%，但成本高 15 倍。月费从 ¥120 变成 ¥1,800——这在规模化时会被放大到不可接受。

**2. 中文能力不输**。目标用户是中国的连锁零售老板，分析报告全是中文。实测中 DeepSeek 对"客单价""退款率""坪效"这些零售术语的理解比 GPT-4o 更准确——后者倾向于英文直译，读起来不自然。

**3. 迁移成本为零**。DeepSeek 的 API 完全兼容 OpenAI 格式，`langchain-openai` 可以直接对接。如果 DeepSeek 出问题，切换到 GPT-4o 只需改一个环境变量。

### 结果

V4 更新后的成本对比更加悬殊：

| 维度 | DeepSeek-V4 | GPT-4o |
|------|:--:|:--:|
| 典型分析成本 | ¥0.03/次 | ¥0.98/次 |
| 年预估成本 | ~¥300 | ~¥8,800 |
| 成本倍数 | 1× | **29×** |

对于连锁零售企业日均 20 次分析的场景，年成本差 ¥8,500。我用 Prompt 优化和 RAG 增强来弥补那 3% 的准确率差距——ROI 远高于换更贵的模型。

<div class="callout"><strong>教训</strong>：选模型不只是选"最好"的，是选"最适合这个场景和成本结构"的。对于 B 端 SaaS，毛利空间直接决定定价空间——模型成本差 15 倍，意味着同样定价下毛利差 15 倍。成本是产品设计的一级约束，不是运维的事。</div>

## D03 为什么 Reflection 只重试 1 次

Reflection（质检 Agent）发现报告质量不达标时，应该反复修改直到通过吗？AI 建议设重试上限 3 次，"确保质量"。我否决了，设为 1 次。

### 冲突

质检的设计初衷是好的：用另一个 LLM 调用检查报告的一致性、逻辑性、可操作性和完整性，发现问题就打回去重写。但问题是——每次重试意味着多一次完整的 LLM 调用，耗时 8-15 秒。3 次重试 = 多等 45 秒。用户从点击"分析"到看到报告，总共可能等 60 秒以上。

这不是假设。我在早期测试时跑过 Reflection 死循环——质检 Agent 反复要求重写，3 次都没通过，用户等了 90 秒后关掉页面。（详见 [BadCase-004：Reflection 死循环](/cases/badcase-004-reflection-loop/)）

### 我的判断

AI 的建议是"质量优先，多试几次"。但我认为这个建议忽略了两个关键因素：

**1. 边际收益递减**。我跑了实测数据：

| 重试次数 | 累计修复率 | 边际修复 |
|---------|:--:|:--:|
| 0 次（直接输出） | ~60% | — |
| 1 次 | ~80% | +20% |
| 2 次 | ~90% | +10% |
| 3 次 | ~92% | +2% |

第一次重试修复了 80% 的问题，第二次只额外修复 10%，第三次几乎无改善。用 45 秒换 2% 的改善——不值。

**2. "够好" > "完美"**。用户宁愿看到一份 85 分的报告（45 秒内），也不愿等 3 分钟看到一份 90 分的。这不是用户的耐心问题，是产品体验的基本逻辑：等待的焦虑比报告的小瑕疵更伤体验。

### 结果

最终方案：最多 1 次重试。如果仍未通过质检，标注"质检未完全通过"但仍输出报告——把判断权交回用户。

质检通过率约 85%（直接通过），首次重试后提升到 95%。用户等待时间控制在 45 秒以内。

<div class="callout"><strong>教训</strong>：<strong>85 分 / 45 秒 > 95 分 / 60 秒</strong>。追求用户可接受的阈值，而非完美——这是 AI 产品体验设计的底线逻辑。Reflection 的价值不在于"保证每次都完美"，而在于"挡住明显错误"。</div>

## D05 为什么用本地 BGE-M3 而非 OpenAI Embedding

V2 引入向量记忆检索时，需要选 Embedding 模型。AI 推荐 OpenAI 的 `text-embedding-3-small`，1536 维，"质量最高"。我否决了，选了本地部署的 BGE-M3。

### 冲突

Embedding 听起来是个小事——把文本变成向量而已。但 EIA 的场景是：每次分析都会生成一条历史记录，需要 Embedding 后存入 pgvector 做相似搜索。这意味着 Embedding 调用量与分析量 1:1 绑定，长期累积。

如果用 OpenAI Embedding，每次分析需要 2 次 API 调用（1 次存储 + 1 次检索），每次调用有 200-500ms 的网络延迟。对于 P95 响应时间目标是 45 秒的系统，多 1 秒的延迟都是奢侈。

### 我的判断

**1. 成本不能"看着小就忽略"**。单次 Embedding 调用确实便宜，但乘以历史分析量的累积效应，长期成本不可忽视。而且这还是在"每次分析"层面——如果后续做批量重训练或全量重建索引，成本会一次性爆发。

**2. 延迟是体验杀手**。本地 Ollama 的 BGE-M3 响应时间 < 50ms，远程 API 是 200-500ms。10 倍延迟差，在用户感知层面就是"秒回"和"转圈"的区别。

**3. 中文效果实测更优**。BGE-M3 在中文语义理解基准 C-MTEB 上排名前列。实测中，对于"华东区销售额下滑原因"这类中文查询，BGE-M3 的相似分析匹配准确率约 79%，优于 OpenAI 的 `text-embedding-3-small`。

### 结果

- Embedding 环节成本归零
- 检索延迟 < 50ms
- 相似分析匹配准确率约 79%
- 无网络依赖，断网环境仍可工作

<div class="callout"><strong>教训</strong>：能本地化、能零成本的环节绝不外购。<strong>每一笔 AI 调用成本都要进产品账本</strong>。Embedding 不像 LLM 调用那样显眼，但它是一个"沉默成本"——在规模化时悄悄吃掉利润。</div>

## D09 为什么 Feature Flag 默认全部关闭

V3 新增了 8 个功能开关——多轮对话、图表推荐、数据溯源、移动端 UI、用户反馈、APM 追踪、友好错误页、Prompt YAML 热重载。AI 建议直接上线，"不需要开关，减少代码复杂度"。我否决了，全部默认关闭。

### 冲突

AI 的逻辑是：功能写好了就该上线，Feature Flag 增加代码分支和测试复杂度，"没必要"。

但 EIA 是一个已有用户在使用的系统。新功能可能引入 LLM 调用次数增加（如多轮对话会让每次分析的 Token 消耗翻倍）、响应变慢（如图表推荐需要额外的 Chart Advisor Agent 调用）、甚至兼容性问题（如移动端 UI 在某些设备上的渲染异常）。如果没有开关，出问题就只能改代码重新部署——用户在等待修复期间持续受影响。

### 我的判断

Feature Flag 不只是安全开关，它同时是三件事：

**1. 灰度安全网**。多轮对话、图表推荐等功能可能引入副作用。Feature Flag 允许在出问题时一键回退，不影响核心分析功能。运维不需要等代码修复和部署。

**2. A/B 测试基础设施**。Flag 让我可以按用户分流到不同版本做对比测试。这个能力后来直接支撑了 4 组关键 A/B 测试：

| A/B 测试 | 对照组 | 实验组 | 核心数据 |
|---------|--------|--------|---------|
| 图表 vs 纯文本 | 无图表 | 含 ECharts 图表 | 阅读耗时 **-64%**，满意度 **+67%** |
| 有溯源 vs 无溯源 | 无溯源标记 | 含可点击溯源 | 信任度 2.5→4.5（**+80%**） |
| 快捷问题 vs 空白框 | 纯输入框 | 6 个快捷问题按钮 | 首次提问 35s→5s（**-86%**） |
| 追问 vs 无追问 | 无追问 | 3 个追问建议 | 对话轮次 1→3（**+200%**） |

没有 Feature Flag，这些测试根本做不了——你不能在生产环境改代码做 A/B。

**3. 运维友好**。如果某个功能在生产环境出现兼容性问题，运维可以立即关闭，不需要等开发改代码和部署。这在 B 端场景里尤其重要——客户不会等你的 CI/CD 流水线跑完。

### 结果

经过 137 条测试验证后，所有 Feature Flag 已从默认关闭改为默认开启。但这不意味着 Flag 没用了——它仍然是后续 A/B 测试和新功能灰度的基础设施。

<div class="callout"><strong>教训</strong>：<strong>保留人工干预入口</strong>。AI 结论可解释、有反馈、可回滚——这三条是 AI 产品设计的底线，不是锦上添花。Feature Flag 的成本是多写几行 if-else，收益是随时可以关掉出问题的功能——这个 trade-off 在任何 AI 产品里都成立。</div>

## 其余 9 条决策速览

### D01 为什么引入 LangGraph 而非 AgentExecutor

经营分析需要 Sales / CRM / Finance 多个系统**并行查询**。AgentExecutor 不支持并行扇出，串行执行会让等待时间翻 3 倍。选 LangGraph 的 `StateGraph` + `Send` 做并行分支，整体分析耗时从 **45s 降到 15s**。技术选型不是追最流行，而是最匹配核心业务约束。

### D04 为什么选响应式 Web 而非小程序

小程序需要独立代码库双端维护，每次 Prompt 优化或 UI 微调都要等 1-3 天审核。老板在手机上的场景是"看一眼今日快报"，响应式 Web 完全覆盖。一次开发多端适配，免去审核周期。先验证核心链路，再考虑渠道形态。

### D06 为什么 V1 推倒重构 V2

V1 的线性函数调用架构从根本上不支持并行。V1 验证了核心链路可行（约 1 周），推倒用 LangGraph 重建 V2 花了约 2 周。如果选择渐进改进，预计也需 2 周但代码质量差得多。V2 架构清晰，后续功能扩展速度显著快于打补丁。先行动再讨论，用重构消灭一类问题。

### D07 为什么设计"查询型 + 分析型"双模式

用户问"各门店销售额排名"只需要一张表，给他 6 段报告就是信息过载。Supervisor 判断问题类型：查询型 → 表格输出，分析型 → 6 段报告。查询型问题平均响应时间**缩短 40%**。不同业务动作对"快/深"的诉求不同，产品要按场景而非按技术给入口。

### D08 为什么用户反馈用 👍/👎 而非 5 星评分

5 星评分要求用户在 5 个选项中选择，增加认知负担。B 端工具场景下用户只想快速表达"好"或"不好"。5 星评分大部分选 3-4 星（中间值），区分度反不如二分类。"这个报告不准确"比"这个报告 3 星"更有行动指导意义。

### D10 为什么建离线评估集

Prompt 优化不能靠感觉。建了 20 条固定评估集（查询型/分析型/边界型三类），每次 Prompt 改动都跑一遍对比。每次改动记录"动了什么、为什么动、修改前后对比、验证数据"。AI 产出质量波动大，没有量化评估集，优化就是盲人摸象。

### D11 为什么设计 RLS 权限注入

企业级 AI 第一优先级是安全与数据隔离。行级权限（RLS）在查询时注入 SQL，确保租户间数据不串。具体案例：用户问"华东区销售额"，RLS 自动注入 `WHERE store_id IN (该用户可见门店)`——即使用户没有指定，也查不到无权限的数据。模型会越来越好，但企业级落地约束不会消失。

### D12 为什么设计 Aggregator 而非让 Agent 互相调用

避免跨领域结论污染（比如用销售数据去推断财务结论）。各领域 Agent 先独立产出，再由 Aggregator 做纯 Python 拼接汇总——**零 Token 消耗**。隔离了就消灭一类 bug：跨领域错误不是"模型不够聪明"，是架构没隔离。

### D13 为什么做一键 Docker 部署

V3 部署需要手动安装 Python 依赖、配置 PostgreSQL/Redis/Ollama、运行迁移、拉取模型，首次部署平均 2 小时。投入 3 天做 `deploy.sh` + `docker-compose.prod.yml` + 预打包 BGE-M3 模型，部署时间从 **2 小时 → 5 分钟**。实施成本是 B 端产品被拒的隐形杀手——客户在安装阶段就放弃了。
