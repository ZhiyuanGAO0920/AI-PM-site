## 001 ｜ RLS 注入跨系统边界

- **现象**：店长有 5 家店权限，问"查哪几家门店"→ SQL 执行失败，返回 `"SQL execution failed: column "store_id" does not exist"`
- **根因**：`store` 表主键列名是 `id`，但 RLS 权限注入代码无脑拼 `WHERE store_id IN (...)`——两个子系统（SQL 生成 + RLS 注入）各自都过了测试，但它们交界处的字段名不一致没人覆盖
- **修复**：加 `_detect_store_column()` 动态识别主键列名——`FROM store` 用 `id`，`FROM orders/inventory` 用 `store_id`
- **影响**：约 **12%** 的首次查询触发此 bug，用户首印象直接崩
- **教训**：**Bug 大多发生在子系统交界处**，不在你最自信的核心逻辑里。详见 [BadCase-001 深度复盘](/cases/badcase-001-rls-injection/)。

## 002 ｜ 追问建议不相关

- **现象**：报告底部的"继续追问"点击率仅 **40%**。用户问"华东区销售为什么下降"，3 个追问却是"会员总数""退款率最高门店""各区域对比"——与本次报告数据毫无关联
- **根因**：Prompt 太模糊——`"生成 3 个追问"`，模型自由发挥，问的都是"通用好问题"而非"基于这次数据的深度问题"
- **修复**：加硬约束：至少 1 条基于报告具体数据 + 至少 1 条挖异常/风险原因 + 覆盖不同维度
- **结果**：点击率 **40% → 100%**
- **教训**：模糊的需求翻译成精确约束，输出质量立刻不同。AI 的"建议"类输出，瓶颈不在广度而在相关性。

## 003 ｜ 隐式 LIMIT 截断排名

- **现象**：用户问"各门店销售额排名"（期望 100 行完整排名），Agent 只返回 20 行，末尾标注"仅展示 TOP 20"——长尾数据被悄悄截断
- **根因**：LLM 在 SQL 生成阶段自作主张加了 `LIMIT 20`。LLM 的默认行为是"过度安全"——宁可少给不多给
- **修复**：在 Supervisor 节点加 `ranking_keywords` 检测（"所有/全部/排名/排行/列表"），命中就追加 `"[系统指令] 列出全部数据行，不允许截断"`
- **教训**：**LLM 默认过度保守，宁可少给**——产品要在关键场景兜底。传统软件 bug 是"给多了"，AI bug 是"给少了"。

## 005 ｜ 知识库过期导致错误回答

- **现象**：佣金规则从"按营业额 5%"改成"按毛利 8%"，但知识库 SOP 文档没同步。**2 周内 30+ 门店**收到错误回答，且 Agent 回答时语气自信——用户无法察觉
- **根因**：业务变更未触发知识库更新，且文档无时间戳标注，Agent 没有检测知识时效性的能力
- **修复**：建立知识库更新 SOP（业务变更 **24h 内**更新）+ 文档 Metadata 加生效日期字段 + Agent 回答时标注"知识来源时间戳"
- **教训**：RAG 的"知识新鲜度"是隐性负债——**过期比缺失更危险**，因为缺失时 AI 会说"不知道"，过期时 AI 会自信地给错答案。

## 006 ｜ 反馈 422 静默丢失

- **现象**：用户点"没有帮助"必定返回 HTTP 422，近 1 个月 **0 条** bad 反馈。产品经理以为"用户很满意"
- **根因**：前端提交 `bad`，后端枚举只认 `helpful|inaccurate|not_relevant`——前端传的值后端不认，静默丢弃。0 条数据其实是全丢了
- **修复**：前后端枚举对齐，前端 `bad` 映射为 `not_relevant`
- **教训**：**0 条数据本身就是红色警报**，不是"用户很满意"。任何"完美数据"都值得怀疑——先查采集链路。

## 007 ｜ 重试率虚高

- **现象**：监控显示重试率 **82.9%**（上月甚至 100%），团队紧张——以为系统大面积出问题
- **根因**：统计 SQL 把 `report` 和 `reflection` 事件都算进 `report_runs` 表。一次正常会话至少 2 条记录（1 次 report + 1 次 reflection），被误判成"1 次正常 + 1 次重试"
- **修复**：统计口径修正——只统计 `event_type = 'report'` 且 `is_retry = true` 的记录
- **结果**：修正后真实重试率 **60.0% / 74.1%**（两个测试环境）
- **教训**：**统计口径错了，比没统计更危险**——假指标会让你对真问题视而不见，还会让团队浪费精力查"根本不存在的问题"。
