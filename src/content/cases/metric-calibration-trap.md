> EIA（Enterprise Insight Agent，企业洞察智能体）项目 V4.6 阶段，我在监控页上连续被四个假指标骗了。这不是模型不够准的问题，是我自己盯的指标口径出了问题。

## 82.9% 重试率：我以为系统快崩了

那天打开监控页，看到一个数字：**近 30 天重试率 82.9%**。上个月更夸张——**100%**。

这意味着几乎所有会话都被判"重试过"。我第一反应：Reflection 质检模块出大问题了，几乎所有报告都没通过质检，全部重跑了一遍。

我开始排查。翻了 Reflection 模块日志，看了质检通过率——**85% 直接通过，首次重试后 95%**。这和 82.9% 的重试率对不上。

根因在指标定义。

监控页的"重试率"统计逻辑是：**只要会话里出现过一次重试，就算"重试过"**。但一次正常分析的全链路包含 Supervisor 路由、3 个领域 Agent 并行查询、Aggregator 聚合、Report Agent 生成报告、Reflection 质检。其中任何一个节点如果触发了重试（比如某个 Agent 的 SQL 语法错误自动修复了一次），整个会话就被标记为"重试过"。

也就是说，82.9% 不是"82.9% 的报告质量不合格"，而是"82.9% 的会话中至少有一个环节发生过一次重试"。这两个含义差了十万八千里。

修复方式：把指标拆成两层——**会话级重试率**（有多少会话涉及重试）和**报告级重试率**（有多少报告被 Reflection 打回）。修复后，会话级 60.0%，报告级 74.1%。

这个数字依然不低，但至少我能从里面看出真正的问题在哪了。

**指标先于优化——指标口径错了，一切优化方向都是错的。AI 产品经理盯指标，第一件事是校验口径。**

## "没有帮助"按钮提交必 422：一个月零差评

第二个假指标更隐蔽。

监控页上有一个反馈统计：用户点"有帮助"和"没有帮助"的分布。我看到的数据是——**近一个月，"没有帮助"的提交数：0**。

零差评。是产品好到没用户不满意吗？

不是。是**"没有帮助"按钮一点就报 422 错误**，根本提交不上去。

根因：前端提交反馈时，`type` 字段传的是 `"bad"`，但后端的枚举只接受 `"helpful"` / `"inaccurate"` / `"not_relevant"`。`"bad"` 不在枚举里，后端直接返回 422 Unprocessable Entity。

用户点"没有帮助" → 前端传 `{"type": "bad"}` → 后端 422 → 前端静默失败 → 用户以为提交了 → 数据库里一条记录都没有。

**一个多月，31 条历史数据全是"有帮助"**——因为"没有帮助"从来没成功提交过。

修复：后端枚举加上 `"bad"`，历史 31 条数据一并 UPDATE 归入正确分类。

这件事让我意识到：**反馈数据的价值在于能驱动分析闭环。但如果反馈通道本身是坏的，你看到的"好数据"比没有数据更危险——因为你会基于假数据做出错误判断。**

## 45 秒看门狗误杀慢查询：用户以为产品坏了

第三个假指标跟超时有关。

用户反馈：综合分析类问题经常报"分析超时（45 秒无响应）"。监控页上超时率居高不下。

我以为是 LLM 调用太慢。但翻日志发现：**节点内部单步 LLM 调用实测 40-75 秒**。一次综合分析的全链路耗时 **165-246 秒**。

问题不在 LLM 慢，问题在前端的 45 秒看门狗。

看门狗逻辑：前端发起 SSE 请求后，如果 **45 秒内没有收到任何事件**，就判定连接挂死，主动 abort。

但 LLM 调用期间（40-75 秒），后端不会推送任何 SSE 事件——因为 LLM 还在生成。前端 45 秒看不到事件，就以为连接断了。

实际上，后端正在正常工作，只是需要 165 秒才能出结果。但前端 75 秒就把连接杀了。

修复：每 20 秒穿插一个 heartbeat 事件（`{"event": "heartbeat"}`），重置看门狗计时器。heartbeat 没有业务含义，只是告诉前端"我还活着"。修复后最大静默 20 秒，看门狗不再误杀。

**慢不是 bug，超时不处理才是。** 如果你的系统确实需要 165 秒，你应该告诉用户"正在分析，预计 3 分钟"，而不是假装 45 秒就能出结果然后在 45 秒时把连接杀了。

## 饼图灰色圆环：字段名差一个下划线

第四个假指标出现在前端渲染层。

React 版前端渲染饼图时，出现了一个灰色空白圆环——饼图框架在，但数据没填进去。

排查发现：后端图表契约中，字段名是 `x_data`（下划线），但 React 前端的 `extractCharts` 函数读的是 `xData`（驼峰）。**差一个下划线，数据映射成空数组**，饼图画了个空壳。

这个问题在旧的 Vanilla JS 前端上不会出现——因为旧前端用的也是 `x_data`。但 React 版迁移时，有人按驼峰命名规范改了字段名，没有同步更新解析逻辑。

修复：在 `extractCharts` 中做归一化，同时接受 `x_data` 和 `xData`。历史报告自动恢复正常显示，分享页也共用同一条管线，一并修好。

**字段契约前后端必须有单一来源。** 解析层修复比渲染层修复收益大——修一个字段映射，省掉每个图表组件各写一遍容错逻辑。

## 四个假指标的共同模式

回头看这四个问题，有一个共同模式：**指标本身没坏，但指标的口径跟你的预期不一致**。

- 重试率 82.9% 是真的——但它统计的是"会话级"不是"报告级"
- 零差评是真的——但那是因为差评通道坏了
- 超时率高是真的——但那是因为看门狗太激进
- 饼图空白是真的——但那是因为字段名差一个下划线

每个指标都在"正确地"统计一个"不对"的东西。

传统产品经理盯的是"用户做了什么"——点击率、转化率、留存率。AI 产品经理还要多盯一层：**"我统计的指标，到底在说什么？"**

这不是挑数据毛刺，是校验指标定义。因为 AI 产品的链路太长——用户提问、Supervisor 路由、多个 Agent 并行查询、Aggregator 聚合、Report 生成、Reflection 质检——每一层都可能产生"重试""超时""失败"这些标签。如果你不明确指标统计的是哪一层，你看到的数字就是个摆设。

我后来给自己定了一条规矩：**每个新上监控页的指标，必须写清楚统计口径——哪一层、什么条件、什么时间窗口。写不清楚的，不上页面。**
