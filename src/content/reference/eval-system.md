> AI 产出质量波动大，没有量化评估集，优化就是盲人摸象。**上线不是终点，是评估起点。**

数据来源：EIA 项目 `run_eval.py`（265 行评估脚本）+ `eval_set.json`（20 条测试集）+ `A-B测试记录.md`（4 组实测）+ 真实运行数据。

## 一、为什么要评估

传统产品的质量是确定性的——功能写好了就 work，测试通过就稳定。AI 产品不是——同一个 Prompt 跑两次可能出不同结果，换个模型可能准确率掉 10%，加一句话上下文可能从"对"变"错"。

没有评估体系会发生什么？

- **改了 Prompt 不知道变好还是变坏**——凭感觉调，调完觉得"好像好了一点"，实际可能更差
- **换模型不敢换**——不知道新模型在你的场景下表现如何
- **A/B 测试做不了**——没有对照组的量化基线
- **用户说"不好用"但不知道哪里不好**——没有指标定位问题

## 二、EIA 的五维指标体系

```
┌─────────────────────────────────────┐
│ 准确性 — SQL 生成准确率 ≥ 85%        │
│ 质量   — Reflection 通过率 ≥ 85%     │
│ 效率   — P95 响应时间 ≤ 60s          │
│ 安全   — 幻觉率 < 2%（实测 0%）       │
│ 成本   — 单次分析 ≤ ¥0.05            │
└─────────────────────────────────────┘
```

| 维度 | 指标 | 目标 | EIA 实测 | 评估方法 |
|------|------|------|---------|---------|
| 准确性 | SQL 生成准确率 | ≥ 85% | 85% | 20 条评估集 |
| 质量 | Reflection 通过率 | ≥ 85% | 95%（含重试） | 离线 eval |
| 效率 | P95 响应时间 | ≤ 60s | 45s | APM 追踪 |
| 安全 | 幻觉率 | < 2% | 0% | 人工抽检 + 溯源 |
| 成本 | 单次分析成本 | ≤ ¥0.05 | ¥0.03 | Token 计费统计 |

> **关键**：五个维度不是独立的，而是互相约束。压成本可能伤准确性，追质量可能伤效率。AI PM 的工作就是在五个维度之间做 trade-off——详见 [决策案例 D02/D03](/cases/decision-cases/)。

## 三、评估集怎么建

EIA 用 20 条固定评估集，分三类：

| 类型 | 数量 | 特征 | 示例 |
|------|------|------|------|
| 查询型（lookup） | 10 条 | 单表/多表 JOIN 明确查询 | "各门店销售额排名" |
| 分析型（analysis） | 7 条 | 跨领域综合分析 | "华东区销售为什么下降" |
| 边界型（edge） | 3 条 | 模糊/无匹配/异常输入 | "分析一下"（无具体维度） |

每条测试用例包含：
- `expected_agents`：期望激活哪些 Agent
- `expected_dimensions`：期望覆盖哪些分析维度
- `min_result_rows` / `max_result_rows`：期望返回行数范围

**评估脚本** `run_eval.py`（265 行）输出：维度覆盖率、行数合理性、幻觉检测、Reflection 通过率、平均延迟，并按 lookup/analysis/edge 分组统计。

## 四、LLM-as-a-Judge 的坑

用 LLM 评估 LLM 的输出（LLM-as-a-Judge）是常见做法，但有陷阱。

EIA 实测：用同一个 LLM 对同一批 5 条报告做质量评分，**2 条评分不一致**——同一个 Judge、同一份报告、跑两次，打分不同。

| 评估方法 | 一致性 | 成本 | 适用场景 |
|---------|--------|------|---------|
| 人工评估 | 高 | 高（人力） | 少量但关键的评估 |
| LLM-as-a-Judge | 中（2/5 不一致） | 低 | 大规模初筛 |
| 规则评估 | 高 | 极低 | 有明确标准的指标（行数、格式） |

**EIA 的做法**：混合评估——规则评估做基础检查（行数、格式、字段），LLM-as-a-Judge 做质量初筛，人工评估做关键决策验证。不把任何单一方法当唯一标准。

> **教训**：LLM-as-a-Judge 的"不一致"不是 bug，是 feature——它提醒你"质量评估本身就有不确定性"。建评估体系时必须对冲这个不确定性，别把 LLM 评分当金标准。

## 五、A/B 测试：用数据做产品决策

EIA 用 Feature Flag 做了 4 组 A/B 测试，每组有量化数据支撑决策：

| A/B 测试 | 对照组 | 实验组 | 核心数据 | 决策 |
|---------|--------|--------|---------|------|
| 图表 vs 纯文本 | 无图表 | 含 ECharts 图表 | 阅读耗时 **-64%**，满意度 **+67%** | P0 必须开启 |
| 有溯源 vs 无溯源 | 无溯源标记 | 含可点击溯源 | 信任度 2.5→4.5（**+80%**） | P0 必须开启 |
| 快捷问题 vs 空白框 | 纯输入框 | 6 个快捷问题 | 首次提问 35s→5s（**-86%**） | P0 必须开启 |
| 追问 vs 无追问 | 无追问 | 3 个追问建议 | 对话轮次 1→3（**+200%**） | P0 必须开启 |

> 没有 Feature Flag，这些测试做不了——你不能在生产环境改代码做 A/B。详见 [决策案例 D09](/cases/decision-cases/)。

## 六、评估流程

```
测试集（固定 20 条）
    │
    ▼
执行评估（run_eval.py 调真实 API）
    │
    ▼
自动评分（维度覆盖 + 行数 + 幻觉检测）
    │
    ▼
分组统计（lookup / analysis / edge）
    │
    ▼
改进建议（哪些类型的问题最常失败？）
    │
    ▼
回归测试（改完 Prompt 再跑一遍）
    │
    ▼
通过 → 发布 / 不通过 → 继续优化
```

> **关键**：每次改 Prompt 都必须跑评估集对比。没有评估集的 Prompt 优化是"凭感觉调参"——你可能觉得改好了，实际可能引入了回归。
