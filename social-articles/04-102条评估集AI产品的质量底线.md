# 102 条评估集：AI 产品的质量底线怎么守住

"感觉更好了。"

这是我改完一个 Prompt 后最常对自己说的一句话。改完 Prompt，跑两个 case 看着不错，心里觉得"比之前好了"，就发上线了。

直到有一天，用户投诉说"分析质量下降了"。我回去查日志，发现新 Prompt 在我测的那两个 case 上确实更好了，但在其他 20 种问题上变差了。

**"感觉更好了"不是发布标准。** AI 产品的输出是非确定性的，你测 2 个 case 觉得好，不代表 100 个 case 都好。

这就是我为什么要建 102 条离线评估集。

## 问题：AI 输出是非确定性的，传统 QA 不管用

传统软件的质量保证逻辑是：写测试用例，跑通过率，通过就发布。输入 A，期望输出 B，实际输出是 B 就通过。

AI 产品不行。同一个输入，LLM 每次可能返回不同的输出——这不是 bug，是 LLM 的特性。你不能写"输入'华东区销售额'，期望输出包含'下降 12%'"——因为数据在变，LLM 的措辞也在变。

所以传统的"输入→期望输出→对比"的测试模式不适用。你得换一种方式：**不测具体输出，测输出的特征。**

什么特征？

- SQL 能不能跑通（语法正确性）
- 报告有没有覆盖用户问的维度（维度覆盖率）
- 数字跟 SQL 查出来的对不对得上（一致性）
- 有没有出现数据库里不存在的字段或数据（幻觉检测）
- 整体耗时多少（延迟）

这些特征是可量化的，不依赖具体措辞。不管 LLM 怎么组织语言，只要这些特征达标，报告就是合格的。

## 102 条评估集怎么设计的

我按三个维度设计评估集：

### 按问题类型分

| 类型 | 条数 | 测什么 |
|------|------|--------|
| 查询型 | 50 条 | 用户问"华东区销售额"，期望输出表格 + 简要说明。不要求深度分析。 |
| 分析型 | 38 条 | 用户问"华东区销售额为什么下降"，期望输出完整报告：摘要、发现、风险、建议。 |
| 边界型 | 14 条 | 故意问超出系统范围的问题，测系统会不会"硬答"还是"如实说不知道"。 |

边界型是最容易被忽略的。很多 AI 产品在"正常问题"上表现不错，一碰到边界问题就崩——要么硬编一个不靠谱的答案，要么报错。

### 按业务域分

| 业务域 | 条数 | 示例 |
|--------|------|------|
| 销售 | 25 | 各区销售额排名、月环比、同比 |
| 会员 | 18 | 新增会员数、复购率、会员等级分布 |
| 财务 | 15 | 毛利率、成本结构、利润排名 |
| 库存 | 15 | 周转率、缺货率、滞销品 |
| 供应链 | 10 | 采购周期、供应商排名 |
| 综合分析 | 14 | 跨域关联分析，如"销售额下降跟库存有什么关系" |
| 边界场景 | 5 | 问系统范围外的问题 |

### 覆盖核心业务场景

不是随便编 102 个问题。每一条对应一个真实业务场景——区域经理每天会问的问题、店长关心的指标、财务关注的成本结构。这些来自用户调研和真实使用日志。

## 评估流程

每次改 Prompt 或 Agent 逻辑，跑一遍评估集：

```
改 Prompt → 跑 102 条评估 → 对比基线分数 → 决定是否发布
```

具体跑什么指标：

| 指标 | 怎么算 | 及格线 |
|------|--------|--------|
| SQL 准确率 | 生成的 SQL 能跑通且返回正确数据 | ≥ 85% |
| 维度覆盖率 | 报告覆盖了用户问题涉及的维度 | ≥ 90% |
| 幻觉检测 | 报告里有没有数据库中不存在的字段或数据 | = 0 |
| 平均延迟 | 从提问到报告输出的总耗时 | ≤ 45 秒 |

四个指标都达标，才能灰度发布。任何一个下降超过 5%，打回。

## 评估集抓到的真实问题

举两个例子，说明评估集不是"为测而测"——它真的抓到了我在手测时没发现的问题。

### 问题一：隐式 LIMIT 截断

用户问"全部门店销售额排名"。我手测的时候，LLM 生成了正确的 SQL，返回了 20 行数据，报告写着"全部门店排名如下"。看起来没问题。

但评估集里有一条"全部门店排名"的 case，期望输出是 100 行（因为有 100 家门店）。评估发现 SQL 里带了 `LIMIT 20`——LLM 默认加了一个限制，只返回了 20 行。

手测看不出来，因为 20 行看起来"差不多对了"。但实际只有 20% 的数据。

修复：在 Prompt 里加了关键词检测——用户说"所有""全部""全部门""排名"时，注入"不限制返回行数"的指令。

### 问题二：追问不相关

评估集有一条测追问质量的 case：用户看完"华东区销售下降原因"的报告后，系统应该推荐相关的追问。

基线评估发现，追问的点击率只有 40%——推荐的问题跟报告内容不相关。比如报告讲的是销售下降，追问推荐的是"总会员数是多少"。

手测时我觉得追问"看起来还行"。但评估集的维度覆盖率指标显示：追问的维度跟报告维度的重合度只有 30%。

修复：给追问生成加了结构化约束——至少 1 条基于报告中的具体数据，至少 1 条针对异常或风险，不允许重复。修复后点击率从 40% 提到 100%。

## 评估集本身也要迭代

V4.1 的时候，评估集只有 20 条。后来发现 20 条覆盖不了所有业务域，有些域一条都没有，改了 Prompt 之后那些域的表现完全是盲区。

V4.6 扩充到 102 条——50 查询型 + 38 分析型 + 14 边界型，覆盖所有 5 个业务域 + 综合分析 + 边界场景。

评估集不是一次建好就不管了。每次发现新的 BadCase，就加一条进评估集，防止同样的问题再次上线。这跟传统软件的"回归测试"逻辑一样——每个 bug 对应一条测试用例。

## 先验证再规模化

这是我做 AI 产品最核心的一条方法论。

不是"改完 Prompt → 感觉不错 → 上线 → 用户投诉 → 回滚"。而是"改完 Prompt → 跑评估集 → 达标 → 灰度 10% → 看真实数据 → 全量"。

多了两步——评估集和灰度——但省了回滚和道歉的时间。

跳过验证直接全量发布，是 AI 产品翻车最常见的姿势。不是因为不知道要验证，是因为"就改了一小点，应该没问题"的侥幸心理。102 条评估集就是我的反侥幸机制——改了什么不重要，跑过才算数。
