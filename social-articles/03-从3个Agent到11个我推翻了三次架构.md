# 从 3 个 Agent 到 11 个：我推翻了三次架构

做 EIA（Enterprise Insight Agent，企业洞察智能体）这一年，我推翻了三次架构。

不是小修小补，是推倒重来。V1 花了一周写完，V2 用了两周重写，V3 改了一个月，V4 又重构了一遍。

每次推翻都不是因为"架构不够优雅"，是因为前一个版本碰到了具体的瓶颈。这篇文章是我四次迭代的真实记录——每个版本解决什么问题、碰什么壁、为什么不得不推翻。

## V1：能跑，但慢得让人想关掉

V1 的架构很简单：一个 Agent，一个 Prompt，串行处理。

用户问"华东区 7 月销售额为什么下降"——Agent 先生成 SQL 查销售表，等结果回来，再查会员表，再查库存表，最后把所有数据塞进一个 Prompt 生成报告。

全链路串行，每一步等上一步。总耗时：**45 秒**。

45 秒是什么概念？用户点"开始分析"后，屏幕上转了 45 秒才出结果。我给同事演示的时候，中间有 3 秒沉默，他问我："卡住了？"

V1 验证了一个事实：核心链路是通的——自然语言转 SQL、查数据库、生成报告——这条路走通了。但它也暴露了一个问题：**串行架构的响应时间，跟业务域数量成正比**。5 个域串行查，每个域 3-5 秒，加报告生成 15-20 秒，就是 45 秒。如果以后加更多域，会更慢。

V1 的使命是"验证可行性"。一周时间，验证了"自然语言查经营数据"这条路能走。然后它就被我推了。

## V2：第一次拆 Agent，但拆法不对

V2 拆成了 3 个 Agent：销售分析 Agent、会员分析 Agent、库存分析 Agent。

但拆法有问题——我让它们**串行接力**。用户提问后，销售 Agent 先查完，把结果传给会员 Agent，会员 Agent 再传给库存 Agent。

响应时间从 45 秒降到了 35 秒。好了一点，但不够。因为本质上还是串行——只是把一个大 Agent 拆成了三个小 Agent 接力跑。

更麻烦的是，三个 Agent 之间传上下文，每传一次 Prompt 就变长一次。销售 Agent 的结果（可能 2000 token）要传给会员 Agent，会员 Agent 的 Prompt 里既要包含自己的 schema，又要包含前一个 Agent 的结果。到最后一个 Agent 时，Prompt 长度跟 V1 差不多了。

**串行拆 Agent，只是把长链路换成了多个短链路接力。瓶颈没变，只是换了位置。**

V2 跑了两周，我决定推翻。

## V3：第一次尝试并行，但协调出了问题

V3 做了一个关键改变：并行扇出。

我用了 LangChain 的 AgentExecutor，同时启动 5 个领域 Agent（销售、会员、财务、库存、供应链），等它们全部返回后，再由一个汇总 Agent 把结果合并成报告。

理论上，5 个 Agent 并行，总时间应该等于最慢的那个 Agent 的时间（约 8 秒），而不是 5 个加起来。响应时间从 35 秒降到了 20 秒。

但 V3 碰到了新问题。

**第一，AgentExecutor 不支持真正的并行。** 它的底层是串行调用 LLM API——只是封装成了"看起来并行"的接口。实际执行时，5 个 Agent 是一个接一个跑的。我用它的时候以为在并行，实际还是串行，只是多了一层抽象开销。

**第二，结果汇总的上下文爆炸。** 5 个 Agent 各自返回 2000-3000 token 的分析结果，汇总 Agent 的 Prompt 要装下 10000-15000 token 的输入。这比 V1 单 Agent 的 Prompt 还长。汇总 Agent 的注意力被稀释，报告质量明显下降。

**第三，故障没有隔离。** AgentExecutor 的设计是"一个失败全链路失败"。库存 Agent 超时了，整个分析就报错，用户什么都拿不到。

V3 让我意识到：并行不是"同时启动几个 Agent"就行。并行需要解决三个问题——真正的并发执行、结果汇总的上下文控制、单点失败的隔离。AgentExecutor 这三个都没解决。

## V4：11 个节点 + 状态机 + 并行扇出

V4 是最终版本，也是当前线上运行的版本。

我换了技术栈：从 LangChain AgentExecutor 换成了 LangGraph StateGraph。

LangGraph 的 StateGraph 解决了 V3 的三个问题：

**1. 真正的并行——Send API**

StateGraph 的 Send API 允许 Supervisor 节点把状态副本同时发给多个分支。5 个领域 Agent 真正并行执行，总耗时等于最慢的那个（约 8 秒），而不是 5 个相加。

**2. 结果汇总不靠 Prompt——纯 Python Aggregator**

V3 的教训：不要让 LLM 做汇总——上下文太长，注意力被稀释。V4 的 Aggregator 是纯 Python 代码，不做 LLM 调用，不花 token。它把 5 个领域 Agent 的结构化结果按字段合并，输出一个统一的 JSON，再交给 Report Agent 生成报告。

Report Agent 拿到的是结构化数据（不是 5 段自然语言文本），Prompt 短了，注意力集中了，报告质量回来了。

**3. 故障隔离——独立 try/except**

每个领域 Agent 有独立的 try/except。库存 Agent 超时了，其他 4 个 Agent 的结果照常返回。Aggregator 检测到库存数据缺失，在报告里标注"库存数据暂时不可用"。用户拿到的是"少了一块但仍然能用"的报告，不是报错页。

**4. 质检后置——Reflection Agent**

V4 加了 Reflection Agent，在报告生成后做 4 维质检（一致性、逻辑性、可执行性、完整性）。最多重试 1 次——不追求完美，够好就行。

**5. 流式输出——SSE**

V4 用 Server-Sent Events 做流式输出。用户发起分析后，每完成一个步骤就推送一个进度事件。用户看到"销售分析完成""会员分析完成"……而不是盯着空白屏幕等 15 秒。

最终数据：

| 维度 | V1 | V2 | V3 | V4 |
|------|----|----|----|----|
| Agent 数 | 1 | 3 | 5+1 | 11 |
| 执行方式 | 串行 | 串行接力 | 假并行 | 真并行 |
| 响应时间 | 45 秒 | 35 秒 | 20 秒 | 15 秒 |
| 故障隔离 | 无 | 无 | 无 | 有 |
| 质检 | 无 | 无 | 无 | Reflection 4 维 |
| 用户反馈 | "卡住了？" | "还是慢" | "偶尔报错" | "可以接受" |

## 每次推翻，都是因为一个具体的瓶颈

回头看这四次迭代，每次推翻都不是计划好的。都是前一个版本上线后，碰到一个具体的问题，逼着我想新方案。

- V1→V2：45 秒太慢 → 拆 Agent
- V2→V3：串行接力没本质改善 → 改并行
- V3→V4：假并行 + 上下文爆炸 + 无故障隔离 → 换 LangGraph + 纯 Python Aggregator + 独立容错

如果一开始就设计 V4 的架构，我会过度设计——V1 的时候我还不清楚哪些环节需要隔离、哪些 Agent 需要拆。是 V1 的 45 秒告诉我"必须并行"，是 V3 的上下文爆炸告诉我"Aggregator 不能用 LLM"。

**架构不是设计出来的，是迭代出来的。** 先做能跑的最小版本，让真实瓶颈告诉你下一步该改什么。

传统产品经理可能觉得"推翻三次架构"听起来像失败。但在 AI 产品里，这是正常节奏——因为 LLM 的行为是非确定性的，你不在真实环境里跑，不知道哪里会出问题。每次迭代都是在用真实数据校准假设。

我不是在追求架构优雅。我追求的是：用户点"开始分析"后，15 秒内拿到一份能用的报告。V1 到 V4 的三次推翻，都是为这个目标服务的。
