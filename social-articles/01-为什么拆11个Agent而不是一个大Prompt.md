# 我为什么把经营分析拆成 11 个 Agent，而不是一个大 Prompt

去年我做了个决策：把一个连锁零售的经营分析 AI，从"一个超大 Prompt"拆成了 11 个分工明确的 Agent。

当时有人问我：把数据库结构直接塞进一个 Prompt 不也能答？为什么要搞这么复杂？

4 个月的线上验证告诉我，这个拆法是对的。但原因不是"Multi-Agent 更高级"——是三个非常具体的问题，逼着我拆。

## 问题一：3000 token 的数据库结构，撑爆了单 Agent 的注意力

EIA（Enterprise Insight Agent，企业洞察智能体）的数据库有 5 个业务域：销售、会员、财务、库存、供应链。每个域 4-8 张表，加起来 30 多张表、200 多个字段。把全部表结构塞进一个 Prompt，光 schema 就 3000 多 token。

你以为 LLM 能"看到"所有表。实际上，当用户的问的是"华东区 7 月销售额为什么下降"，LLM 的注意力会被最近出现的表结构干扰——它可能在回答销售问题时，突然引用了库存表的字段，因为库存表的 schema 刚好排在 Prompt 最后面。

这不是幻觉，是上下文竞争。LLM 的注意力不是均匀分布的，就像人看一份 50 页报告，最后几页的内容比中间几页记得更清楚。

拆成 11 个 Agent 后，每个领域 Agent 只加载自己那 4-8 张表的 schema。销售 Agent 只看销售表，库存 Agent 只看库存表。注意力集中了，SQL 准确率从 80% 出头提升到 85%-90%。

**拆 Agent 的第一个理由：减少上下文竞争。不是模型不够强，是上下文太长它顾不过来。**

## 问题二：一个节点出错，整个对话就废了

单 Agent 模式下，我踩过一个坑：用户问"全部门店销售额排名"，LLM 生成 SQL 时自动加了 `LIMIT 20`。用户看到的是 Top 20，以为系统里只有 20 家门店——实际上有 100 家。

这个错误发生在 SQL 生成环节。如果只有一个大 Agent，这个错误会直接进入报告生成环节，报告里写"全部门店排名如下"，下面跟着 20 行数据。用户拿到一份"看起来对但实际截断了"的报告。

更麻烦的是：如果这个大 Agent 的 SQL 出错了，整个对话就卡住了——因为报告生成、图表推荐、质量检查全都耦合在一个 Agent 里，一个环节挂了，后面全停。

拆成 11 个 Agent 后：

- 领域 Agent 各自独立查询，SQL 出错只影响那一个域的数据
- Aggregator 聚合时，如果某个域的数据缺失，会在报告里标注"库存数据暂时不可用"
- Reflection 质检能定位到具体哪个环节出了问题，而不是笼统地"报告质量不行"

**拆 Agent 的第二个理由：故障隔离。一个节点的错误不该废掉整个对话。**

## 问题三：改一个 Prompt，牵一发动全身

V1 的时候，所有逻辑写在一个 Prompt 里。有一次我想调整报告的格式——把"建议"部分从 3 条改成 5 条。改完之后，SQL 生成的准确率突然掉了 8 个百分点。

为什么？因为 Prompt 变长了，LLM 的注意力分布变了。我改的是报告格式，影响的是 SQL 生成。这两个任务在同一个 Prompt 里耦合着，改 A 坏 B。

这在传统软件工程里叫"耦合"——两个不相关的功能写在一个模块里，改一个影响另一个。解决方案是拆模块。AI 产品也一样。

拆成 11 个 Agent 后，每个 Agent 有独立的 Prompt：

- 销售分析 Agent 的 Prompt 改了，不影响库存 Agent
- Report Agent 的格式调整了，不影响 SQL 生成
- Reflection 质检标准变了，不影响其他 Agent 的输出

每个 Prompt 独立版本管理，独立 A/B 测试，独立灰度发布。

**拆 Agent 的第三个理由：迭代效率。改一个不该影响全部。**

## 代价是什么

拆 Agent 不是免费的。

**协调成本上升了。** 11 个 Agent 需要 Supervisor 来路由——判断用户的问题该派给哪些领域 Agent。Supervisor 本身就是一个 LLM 调用，多了一层决策开销。如果 Supervisor 路由错了（比如把财务问题派给了销售 Agent），结果就不对。

**响应链路变长了。** 单 Agent 是"提问→生成→回答"三步。11 个 Agent 是"提问→Supervisor 路由→5 个领域 Agent 并行查询→Aggregator 聚合→Chart Advisor 推荐图表→Report Agent 生成报告→Reflection 质检→Memory 存储"——8 步。

**调试难度变大了。** 单 Agent 出错，看一个 Prompt 就行。11 个 Agent 出错，要逐节点排查。我加了全链路 trace_id 追踪，才把调试效率拉回来。

但这些代价，跟"一个 Prompt 改坏了全线崩"相比，是可以接受的。

## 数据印证

| 维度 | 单 Agent（V1） | 11 Agent 并行（V4） |
|------|---------------|-------------------|
| 响应时间 | 45 秒 | 15 秒（并行扇出） |
| SQL 准确率 | 80% | 85%-90% |
| 故障影响范围 | 全链路 | 单个域 |
| Prompt 迭代 | 牵一发动全身 | 独立版本管理 |
| 单次成本 | ¥0.03 | ¥0.03（Agent 分工后调用更精准，总 token 反而更少） |

注意最后一行：拆成 11 个 Agent 后，单次成本没有涨。因为每个 Agent 只加载自己域的 schema，总 token 消耗反而比"一个 Prompt 塞所有 schema"更少。

## 什么时候不该拆

不是所有 AI 产品都需要拆 Agent。如果你满足以下条件，单 Agent 可能就够了：

- 数据表少于 10 张，schema 不超过 500 token
- 用户问题集中在单一域，不需要跨域关联
- Prompt 迭代频率低，改一次能稳定运行很久
- 出错成本低，用户能容忍偶尔答错

EIA 不满足这些条件——30 多张表、5 个业务域、跨域关联查询、B 端用户容错率低。所以拆。

**拆不拆 Agent，不是看"Multi-Agent 是不是趋势"，是看你的问题是否满足三个条件：上下文是否过长、故障是否需要隔离、迭代是否需要独立。**

满足任何一个，就该拆。三个都满足，必须拆。
