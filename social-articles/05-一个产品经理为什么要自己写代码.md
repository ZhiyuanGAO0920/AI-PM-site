# 一个产品经理为什么要自己写代码

做了 6 年 B 端产品经理，我一直信奉一句话："产品经理不需要写代码。"

理解业务、定义需求、协调资源、推动落地——这些才是产品经理的核心能力。代码是工程师的事。

直到我开始做 AI 产品。

## 触发点：一个 PRD 让我动摇了

2024 年，我用 ChatGPT 辅助写一份 PRD。需求是给一个会员系统加状态流转——正常、冻结、注销、恢复，12 个核心场景，每个场景有金额计算规则。

以前这种 PRD 我要写两天。跟业务方确认规则、画状态流转图、列每个场景的输入输出和异常分支。改三版才能定稿。

那天我把业务规则口述给 ChatGPT，它帮我生成了状态流转表、场景描述、异常分支处理。半天搞定。

不是 AI 替我做了决策——12 个场景的业务规则是我定义的，流转逻辑是我设计的。AI 做的是把我的设计翻译成结构化文档，比我手写快 4 倍。

这件事让我意识到：AI 时代的产品经理，跟 AI 的协作方式会变。以前 PM 把需求写清楚，交给工程师做。现在 PM 可以直接跟 AI 协作，把想法快速变成原型。

但前提是：你得知道 AI 能做什么、不能做什么、怎么做。

## 转折点：从"用 AI"到"做 AI 产品"

用 AI 写 PRD 是"用 AI"。做 EIA（Enterprise Insight Agent，企业洞察智能体）是"做 AI 产品"。中间隔着一道坎。

那道坎是：**你不能靠"感觉"判断 AI 能不能做某件事。**

举个例子。EIA 早期有个争论：用一个大 Prompt 查所有业务数据，还是拆成多个 Agent 分别查？

不懂技术的人会说："让 AI 自己判断嘛，它什么都能做。"

但如果你写过 Prompt，你就知道：3000 token 的数据库 schema 塞进一个上下文，LLM 的注意力会衰减。如果你跑过实际 case，你就知道：单 Agent 的响应时间 45 秒，用户等不了。如果你看过 AgentExecutor 的源码，你就知道：它不支持真正的并行。

这些都是"写代码才知道的事"。不写代码的产品经理，做 AI 产品的决策只能靠"听说"和"感觉"。

我不愿意靠感觉做决策。

## 我做了什么

我花了一年时间，自己做了一个完整的 AI 产品。

EIA——连锁零售经营分析平台。11 个 Agent 的 LangGraph 状态机，自然语言查询经营数据，自动生成分析报告。从需求定义、模型选型、Agent 架构设计、Prompt 工程、评估体系搭建，到 Docker 部署，全部自己来。

我写了多少代码？坦白说，不多。核心逻辑大部分是 LLM 在生成——SQL 是 LLM 写的，报告是 LLM 写的，图表推荐是 LLM 做的。我写的是"约束"——状态机的节点连接、Agent 的 Prompt 定义、权限注入的规则、评估集的指标计算。

但这些"约束"才是 AI 产品的核心。模型是公共基础设施，约束是产品私有资产。

## 哪些 B 端能力直接迁移了

做 AI 产品这一年，我发现 6 年 B 端产品经验里，有几项能力直接可用：

**规则抽象能力。** B 端产品的核心是"把复杂的业务规则抽象成可配置的系统方案"。做 AI 产品也一样——只不过抽象对象从"业务规则"变成了"AI 行为"。

比如权限隔离。B 端产品里，区域经理只能看自己区域的订单数据——这是行级权限。EIA 里，Agent 生成 SQL 时要自动注入 `WHERE store_id IN (...)` 限制查询范围——这也是行级权限，只不过注入时机从"查询接口"变成了"SQL 生成环节"。

规则抽象的逻辑一模一样。只是落地点从"接口层"移到了"Prompt 层"。

**用户旅程设计。** B 端产品讲究"用户从哪进来、看到什么、做什么操作、得到什么结果"。AI 产品的用户旅程更长——用户提问、Supervisor 路由、Agent 并行查询、Aggregator 聚合、报告生成、Reflection 质检——每一步都是用户旅程的一个节点。

B 端 PM 设计用户旅程的能力，在设计 Agent 流程时完全适用。区别只是：以前你设计的是"用户在每个页面做什么"，现在你设计的是"Agent 在每个节点做什么"。

**反馈闭环设计。** B 端产品讲究"没有 feedback 的功能不算上线"。AI 产品更需要——没有用户反馈的 AI 功能，你不知道它变好了还是变差了。EIA 每份报告都有 👍/👎 按钮，反馈数据进评估集，驱动 Prompt 优化。

这些都是 B 端基本功，不是 AI 新能力。

## 哪些必须从头学

但有些东西，6 年 B 端经验帮不了我，必须从头学。

**模型能力边界。** 传统软件的功能边界是代码定义的——写了什么功能就有什么功能。AI 产品的功能边界是模型定义的——模型能做到什么，你的产品就能做什么。

你得知道：DeepSeek V4 Flash 的 SQL 生成准确率 85%，不是 99%。Reflection 质检不能保证 100% 抓住所有错误。LLM 默认会在 SQL 里加 `LIMIT 20`，即使你没让它加。这些不是"bug"，是模型的行为模式。

不跑过实验，你不知道这些边界在哪。这是必须"动手"才能学到的东西。

**Prompt 工程。** 这不是"写文案"。Prompt 工程是"用自然语言编程"——你得想清楚变量结构、约束条件、异常处理、输出格式。

EIA 的 Report Agent 的 Prompt 有 2000 多字，包含：角色定义、输出格式模板、分析维度约束、数据引用规则、语气要求、异常处理指引。改一个字都可能影响输出质量。

这跟写 PRD 的逻辑不同。PRD 是给人看的，工程师读了 PRD 会自己判断怎么实现。Prompt 是给机器看的，机器不会"自己判断"——你说的每一句话都会影响输出，包括你没说的。

**评估体系。** 传统软件测"输入 A 输出 B"。AI 产品测"输入 A 输出的特征对不对"。这个思维方式跟传统 QA 完全不同。我从零开始建了 102 条评估集，定义了 SQL 准确率、维度覆盖率、幻觉检测、平均延迟四个指标。

**成本意识。** 传统软件的成本是服务器和人力。AI 产品的成本是 token——每次调用 LLM 都花钱。一个 Agent 重试 8 次，成本涨 10 倍。这些是 B 端产品从来没有过的约束。

## 为什么要自己写代码

回到标题的问题。

不是"产品经理必须会写代码"。是"做 AI 产品时，自己写代码能让你做出更好的决策"。

因为 AI 产品的很多决策——拆不拆 Agent、重试几次、用什么模型、Prompt 怎么写——不是靠"理解业务"就能做的。你得知道技术实现的具体细节，才能做出正确的产品决策。

不写代码的产品经理，做 AI 产品时只能提"方向性建议"：我们应该做智能分析、应该做多 Agent、应该做质量检查。但"智能分析用什么模型""多 Agent 怎么拆""质量检查几维"这些具体决策，需要技术理解。

不是说产品经理要变成工程师。是说 AI 产品经理的技术理解深度，要超过传统 B 端 PM。你不需要自己写生产环境的代码，但你需要能看懂、能跑实验、能基于数据做决策。

我自己写代码，不是因为"想当工程师"。是因为"不想靠感觉做 AI 产品决策"。

## 简历写"精通 AI"没人信

面试的时候，面试官问我："你做过什么 AI 产品？"

如果我回答"我研究过 RAG 架构、了解 Multi-Agent 协作、读过 Agent 论文"——他不会信。因为每个人都能这么说。

如果我回答"我做了 11 个 Agent 的经营分析平台，192 条自动化测试全绿，响应时间从 45 秒优化到 15 秒，单次成本 ¥0.03，代码开源在 GitHub"——他会去看。

然后他会问我每个决策的"为什么"：为什么拆 11 个而不是 5 个？为什么重试 1 次不是 3 次？为什么用 DeepSeek 不用 GPT-4o？

这些"为什么"，不是靠读文章能答的。是靠自己做了一遍、踩了坑、修了 bug、跑了实验，才答得出来的。

**简历写"精通 AI"没人信，把系统开源就是最好的简历。**

不是因为开源证明你"技术强"。是因为开源意味着你的每个决策都可以被验证——面试官能看代码、能跑测试、能问你为什么。

这跟 EIA 的信任设计理念一样：不承诺 100% 准确，承诺 100% 可追溯。

你不需要什么都自己写。但你需要做过一遍，才知道每个环节的约束在哪、代价是什么、什么时候该妥协。

这就是一个产品经理为什么要自己写代码。
