# AI 报告不胡说的工程闭环：从 4 维质检到 192 条测试

> AI 产品最大的信任危机不是"AI 不会"，是"AI 会但说错了，而且语气很自信"。

我做了 6 年 B 端产品，2025 年做了一个 AI 经营分析平台——EIA（Enterprise Insight Agent，企业洞察智能体）。输入"华东区销售为什么下滑"，它 60 秒内查完 5 万笔订单，输出一份带 SQL 溯源和图表的诊断报告。

做 AI 产品后我发现一个问题：**用户不怕 AI 说"不知道"，怕的是 AI 自信地给一个错答案。**

EIA 上线初期出过这样一个场景：佣金规则从"按营业额 5%"改成了"按毛利 8%"，但知识库的 SOP 文档没同步。2 周内 30+ 门店收到错误回答——而且 Agent 回答时语气自信，用户完全无法察觉。

这个 BadCase 教会我一件事：**过期比缺失更危险。缺失时 AI 会说"不知道"，过期时 AI 会自信地给错答案。**

这篇文章讲的是我怎么用工程手段解决这个问题：从 4 维质检到 192 条自动化测试，从离线评估集到 BadCase 复盘体系，搭一套让 AI"不胡说"的工程闭环。

## 一、Reflection：4 维质检 + 重试上限 1 次

EIA 的质检 Agent 叫 Reflection。它的作用不是"让报告更好看"，是"挡住明显错误"。

### 4 维质检

Reflection 检查报告的 4 个维度：

1. **一致性**：报告里的数据是否自洽。比如报告说"华东区销售额下降 15%"，但下面的表格显示的是下降 8%——不一致。
2. **逻辑性**：结论是否有数据支撑。比如报告说"建议增加库存"，但数据里库存周转率已经在下降——逻辑不成立。
3. **可操作性**：报告是否给出了可执行的建议。如果只说"销售额下降"但不给原因和行动建议——不可操作。
4. **完整性**：报告是否覆盖了用户问题的关键维度。用户问"为什么下降"，报告只给了"下降了多少"——不完整。

### 重试上限：为什么 1 次是最优解

Reflection 发现报告不达标时，应该反复修改直到通过吗？

AI 建议设重试上限 3 次，"确保质量"。我否决了，设为 1 次。

实测数据：

| 重试次数 | 累计修复率 | 边际修复 | 额外等待时间 |
|---------|:--:|:--:|:--:|
| 0 次（直接输出） | ~60% | — | 0s |
| 1 次 | ~80% | +20% | 8-15s |
| 2 次 | ~90% | +10% | 16-30s |
| 3 次 | ~92% | +2% | 24-45s |

第一次重试修复了 80% 的问题，第二次只额外修复 10%，第三次几乎无改善。用 45 秒换 2% 的改善——不值。

而且每次重试意味着多一次完整的 LLM 调用，消耗 3000-5000 Token。3 次重试 = 额外 9000-15000 Token，单次成本翻倍。

最终方案：最多 1 次重试。如果仍未通过质检，标注"质检未完全通过"但仍输出报告——把判断权交回用户。

质检通过率约 85%（直接通过），首次重试后提升到 95%。用户等待时间控制在 45 秒以内。

**85 分 / 45 秒 > 95 分 / 60 秒。** 追求用户可接受的阈值，而非完美。

### Reflection 死循环：一个真实的 BadCase

早期测试时，我跑过 Reflection 死循环——质检 Agent 反复要求重写，3 次都没通过，用户等了 90 秒后关掉页面。8 次重试吃掉 50 万 Token，单次成本暴涨 10 倍。

根因：Reflection 的 Prompt 太严格，"完美主义"导致几乎不可能通过。而且没有设重试上限，陷入死循环。

修复：设重试上限 1 次 + 放宽质检标准（85 分通过，不追求 100 分）+ 即便未通过也输出报告（标注"质检未完全通过"）。

**Reflection 的价值不在于"保证每次都完美"，而在于"挡住明显错误"。**

## 二、离线评估集：Prompt 优化不能靠感觉

EIA 建了 20 条固定的离线评估集（V4 扩展到 102 条），覆盖三类场景：

- **查询型**（10 条）：如"各门店销售额排名"——期望表格输出
- **分析型**（7 条）：如"华东区销售为什么下滑"——期望报告输出
- **边界型**（3 条）：如"帮我查一下"——意图模糊，测试系统的兜底能力

每次 Prompt 改动，都跑一遍评估集做对比。记录"动了什么、为什么动、修改前后对比、验证数据"。

没有评估集时，Prompt 优化就是盲人摸象——你觉得改好了，但不知道是真好还是碰巧这一次好。有了评估集，每次改动都有量化对比。

### 一个真实的优化案例

追问建议的 Prompt 从 `"生成 3 个追问"` 改成 `"至少 1 条基于报告具体数据 + 至少 1 条挖异常/风险原因 + 覆盖不同维度"`。

改动前：追问点击率 40%。用户问"华东区销售为什么下降"，3 个追问是"会员总数""退款率最高门店""各区域对比"——与本次报告数据毫无关联。

改动后：追问点击率 100%。追问变成"华东区销售下降 15% 主要受 A 门店影响，是否查看 A 门店详细数据？""退款率从 3% 升到 5%，是否分析退款原因？"——每条都基于报告具体数据。

**模糊的需求翻译成精确约束，输出质量立刻不同。** 这是评估集帮我量化的。

## 三、192 条自动化测试：AI 产品的质量观

传统软件测试验证"输入 A 永远得到 B"。AI 产品的输出有概率性——同一个输入可能得到 B 或 B'。这意味着 AI 产品的测试策略要不一样。

EIA 的 192 条测试覆盖三个层面：

### 1. 链路测试（约 80 条）

验证完整链路是否跑通：输入 → Supervisor 路由 → Agent 查询 → Aggregator 汇总 → Report 生成 → Reflection 质检 → 输出。

这些测试不验证输出内容的准确性（因为输出有概率性），只验证"流程不断、不崩、不超时"。

### 2. 功能测试（约 60 条）

验证各功能开关的行为：Feature Flag 开/关时，多轮对话、图表推荐、数据溯源、移动端 UI 等功能是否按预期工作。

经过 137 条测试验证后，所有 Feature Flag 已从默认关闭改为默认开启。

### 3. 边界测试（约 50 条）

验证异常场景：空查询、超长输入、无权限数据、数据库连接失败、LLM 超时。这些测试确保系统在异常情况下不崩溃，而是给出友好的降级响应。

### 测试的局限

AI 产品的测试无法做到 100% 覆盖——因为 LLM 的输出空间是无限的。192 条测试覆盖的是"已知场景"和"已知边界"，但线上一定会出现测试集没覆盖的新 Case。

这就是为什么 BadCase 复盘体系同样重要——它不是测试的替代，是测试的补充。

## 四、BadCase 复盘体系：从"修一个 bug"到"消灭一类 bug"

EIA 有 7 条 BadCase 复盘记录，每条按"现象 → 根因 → 修复 → 教训"四段写。以下 4 条最能说明问题。

### BadCase-001：RLS 权限注入跨系统边界

**现象**：店长有 5 家店权限，问"查哪几家门店"→ SQL 执行失败。

**根因**：`store` 表主键列名是 `id`，但 RLS 权限注入代码无脑拼 `WHERE store_id IN (...)`。两个子系统各自都过了测试，但交界处的字段名不一致没人覆盖。

**影响**：约 12% 的首次查询触发此 bug。

**教训**：Bug 大多发生在子系统交界处，不在你最自信的核心逻辑里。

### BadCase-003：隐式 LIMIT 截断排名

**现象**：用户问"各门店销售额排名"（期望 100 行完整排名），Agent 只返回 20 行，末尾标注"仅展示 TOP 20"——长尾数据被悄悄截断。

**根因**：LLM 在 SQL 生成阶段自作主张加了 `LIMIT 20`。LLM 的默认行为是"过度安全"——宁可少给不多给。

**修复**：在 Supervisor 节点加 `ranking_keywords` 检测（"所有/全部/排名/排行/列表"），命中就追加 `"[系统指令] 列出全部数据行，不允许截断"`。

**教训**：传统软件 bug 是"给多了"，AI bug 是"给少了"。LLM 默认过度保守，产品要在关键场景兜底。

### BadCase-005：知识库过期导致错误回答

**现象**：佣金规则从"按营业额 5%"改成"按毛利 8%"，知识库 SOP 文档没同步。2 周内 30+ 门店收到错误回答，且 Agent 回答时语气自信——用户无法察觉。

**根因**：业务变更未触发知识库更新，文档无时间戳标注，Agent 没有检测知识时效性的能力。

**修复**：建立知识库更新 SOP（业务变更 24h 内更新）+ 文档 Metadata 加生效日期字段 + Agent 回答时标注"知识来源时间戳"。

**教训**：RAG 的"知识新鲜度"是隐性负债。**过期比缺失更危险**——缺失时 AI 会说"不知道"，过期时 AI 会自信地给错答案。

### BadCase-006：反馈 422 静默丢失

**现象**：用户点"没有帮助"必定返回 HTTP 422，近 1 个月 0 条 bad 反馈。产品经理以为"用户很满意"。

**根因**：前端提交 `bad`，后端枚举只认 `helpful|inaccurate|not_relevant`——前端传的值后端不认，静默丢弃。0 条数据其实是全丢了。

**修复**：前后端枚举对齐，前端 `bad` 映射为 `not_relevant`。

**教训**：**0 条数据本身就是红色警报**，不是"用户很满意"。任何"完美数据"都值得怀疑——先查采集链路。

## 五、金丝雀部署：怎么检测大模型"偷偷变笨"

AI 产品有一个传统软件没有的问题：**模型供应商会静默更新模型版本。** 你的 Prompt 没变、代码没变，但模型行为变了——准确率可能悄悄下降。

EIA 的解决方案是"金丝雀闭环"：

### 1. eval_runs 落库带模型版本

每次评估运行的记录都带模型版本号。如果模型供应商静默更新了版本，你能在评估数据里看到准确率的变化，并定位到是哪个版本导致的。

### 2. 16 条固定子集每日跑分

从 102 条评估集里抽 16 条核心 Case，每天自动跑一遍。如果准确率下降超过阈值（比如 5%），自动告警。

### 3. 漂移告警

监控 SQL 准确率、Reflection 通过率、幻觉率。任何指标连续 3 天下降趋势，触发告警通知。

这套体系确保：**即使模型供应商偷偷更新了模型，你也能在 24 小时内发现准确率漂移，而不是等用户投诉。**

## 六、质量监控的真实数据

EIA V4.1 的质量指标：

| 指标 | V2 | V4.1 | 优化手段 |
|------|:--:|:--:|---------|
| SQL 准确率 | 85% | 90% | Prompt 迭代 + 评估集对比 |
| Reflection 通过率 | 85% | 90% | 4 维质检 + 重试 1 次 |
| P50 延迟 | 45s | 30s | 并行扇出 + 流式输出 |
| 幻觉率 | 未测 | < 2% | Reflection 质检 + 数据溯源 |
| 单次成本 | ¥0.04 | ¥0.03 | DeepSeek + 本地 Embedding |
| 评估集 | 20 条 | 102 条 | 持续积累 BadCase |

这里有一个真实的成本追踪坑：原本用全局 `CostTracker` 报固定 ¥0.04，实际是假象。改成 `ContextVar` per-task 后才是真值 ¥0.03——全局追踪在并行场景下会丢失部分调用记录。

**统计口径错了，比没统计更危险。** 假指标会让你对真问题视而不见。

## 七、可复制的方法：AI 质量体系的 4 层防线

如果你也在做 AI 产品，以下是 EIA 验证过的 4 层质量防线：

**第 1 层：Reflection 质检（挡住明显错误）**

用另一个 LLM 调用检查输出的 4 个维度（一致性/逻辑性/可操作性/完整性）。重试上限 1 次——追求 85 分 / 45 秒，不追求 95 分 / 60 秒。

**第 2 层：离线评估集（量化优化效果）**

建 20 条以上固定评估集，覆盖查询型/分析型/边界型。每次 Prompt 改动都跑一遍对比，记录"动了什么、修改前后对比"。

**第 3 层：BadCase 复盘（从修 bug 到消灭 bug）**

每条 BadCase 按"现象→根因→修复→教训"四段写。修表象和修根因的区别，是"减少一个 bug"和"消灭一类 bug"的区别。

**第 4 层：金丝雀监控（检测模型漂移）**

eval_runs 落库带模型版本，16 条固定子集每日跑分，漂移告警。确保模型供应商静默更新时你能发现。

## 写在最后

这篇文章的核心观点可以用一句话概括：

**AI 产品的信任不在"AI 多聪明"，在"出了错你能多快发现、多快修复"。**

Reflection 挡住明显错误，评估集量化优化效果，BadCase 复盘消灭一类 bug，金丝雀监控检测模型漂移。这 4 层防线不是"锦上添花"，是 AI 产品从 Demo 到可运营系统的必经之路。

AI 产品的竞争壁垒不在模型能力——模型是公共基础设施。壁垒在这些工程约束的积累：RLS 权限注入、Reflection 质检、评估体系、漂移告警。这些坑只有做过才知道怎么防。
