# 为什么把经营分析拆成 11 个 Agent，而不是一个大 Prompt

> 4 个月的线上验证告诉我：一个超级 Prompt 解决不了的问题，不是 Prompt 不够好，是架构不对。

去年我做了第一个 AI 产品——EIA（Enterprise Insight Agent，企业洞察智能体）。它的核心功能很简单：用户输入一句话，比如"华东区销售为什么下滑"，系统 60 秒内查完 5 万笔订单、跨 3 个业务域交叉验证，输出一份带 SQL 溯源和图表的诊断报告。

V1 版本我用了最直觉的做法：一个大 Prompt，把数据库结构、业务知识、输出格式全塞进去，让一个 Agent 干所有事。

结果 45 秒响应、报告格式混乱、一个节点出错整个对话就废了。

V4 版本，我把它拆成了 11 个分工明确的 Agent。响应时间降到 15 秒，192 条测试全绿，7 条 BadCase 全部复盘归档。

这篇文章讲的是从 V1 到 V4 的架构演进决策：为什么拆、拆了付什么代价、哪些代价可以省。

## 一、V1 的问题：上下文竞争

V1 只有 1 个 Agent，约 2000 行代码。我把数据库结构（约 3000 Token）、业务知识、输出格式约束、数据溯源规则全部塞进一个 Prompt。

这个做法的问题不是"跑不通"——技术上能跑。问题是三个层面：

### 1. 注意力衰减

LLM 的注意力不是均匀的。当 Prompt 里有 3000 Token 的数据库结构 + 大量业务知识 + 输出约束时，模型对每个部分的关注度都会下降。

实测中，V1 的 SQL 生成准确率约 85%。但如果你单独把 SQL 生成任务拎出来，只给相关表结构和查询意图，准确率能到 90%——那 5% 的差距就是上下文竞争造成的。

3000 Token 的数据库结构塞进一个上下文，模型的注意力被分散了。它不是"不知道"怎么写 SQL，是"被太多信息干扰了"。

### 2. 故障不隔离

V1 的架构是线性的：理解意图 → 生成 SQL → 执行 SQL → 生成报告。如果 SQL 生成环节出问题（比如幻觉了一个不存在的字段名），后面所有环节都受影响——报告基于错误数据生成，质检也无法发现问题（因为它不知道数据是错的）。

一个节点出错，整个对话就废了。

### 3. 迭代牵一发动全身

V1 的 Prompt 是一个整体。改报告生成的约束，可能影响 SQL 生成的行为——因为它们在同一个上下文里。每次改动都要全量回归测试，迭代效率极低。

## 二、V2：拆成多 Agent 并行

V2 做了两个核心改变：引入 LangGraph 做并行扇出，和拆分领域 Agent。

### 为什么选 LangGraph 而非 AgentExecutor

AgentExecutor 不支持并行扇出。EIA 的场景需要 Sales、CRM、Finance 三个系统并行查询——串行执行的话，等待时间翻 3 倍。

选 LangGraph 的 `StateGraph` + `Send` 做并行分支，3 个 Agent 同时查库，整体分析耗时从 45 秒降到 15 秒。

技术选型不是追最流行，而是最匹配核心业务约束。

### 扇出扇入架构

V2 的链路：
```
Supervisor（temperature=0，路由决策）
  → LangGraph Send 并行扇出
    → Sales Agent（查销售数据）
    → CRM Agent（查会员数据）
    → Finance Agent（查财务数据）
  → Aggregator（纯 Python 拼接，零 Token）
  → Report（SSE 流式输出报告）
```

这里有一个关键设计：**Aggregator 用纯 Python 做数据拼接，零 Token 消耗**。

为什么不用 LLM 做汇总？因为数据拼接是确定性逻辑——把三个 Agent 的查询结果按格式合并。确定性事务交给代码，模糊判断交给 AI。如果让 LLM 做汇总，不仅多花钱，还可能引入幻觉（比如把销售数据错误地关联到财务结论上）。

### 兜底机制

Supervisor 如果 LLM 调用失败，用关键词匹配兜底（"销售"→sales Agent），不整体崩。这保证了即使 LLM 出问题，系统也不会完全不可用。

## 三、V3→V4：从"好不好用"到"企业级"

V2 解决了速度问题，但用户体验和企业级要求没解决。

### V3：体验打磨

V3 加了流式输出（SSE）。95%+ 的查询是新问题，缓存命中极低，所以流式优先——用户看到进度条一步步亮起来，比等 15 秒后一次性出结果体验好得多。

但这里踩了一个真实的坑：节点内非流式 LLM 调用单步 40-75 秒无事件，前端 45 秒看门狗误判"分析超时"。整体实测 165-246 秒必超时。

修复方案：`_with_heartbeat` 每 20 秒发一个 `{"type":"heartbeat"}`，最大静默不超过 20 秒。前端知道系统还在干活，不会误判超时。

V3 还加了 Feature Flag（8 个功能开关，默认全部关闭），为后续 A/B 测试打下基础设施。

### V4：企业级 + 质量体系

V4 达到了最终形态：11 节点、多租户、192 条测试。

11 个节点分别是：
1. Supervisor（路由决策）
2-4. 三个领域 Agent（Sales / CRM / Finance）
5. Aggregator（纯 Python 汇总）
6. Chart Advisor（图表推荐）
7. Report（报告生成，SSE 流式）
8. Reflection（4 维质检）
9-10. 两个辅助节点（知识检索 + 限流）
11. RLS 权限注入层

V4 的质量监控数据：

| 指标 | V2 | V4 |
|------|:--:|:--:|
| SQL 准确率 | 85% | 90% |
| Reflection 通过率 | 85% | 90% |
| P50 延迟 | 45s | 30s |
| 幻觉率 | 未测 | < 2% |
| 单次成本 | ¥0.04 | ¥0.03 |
| 评估集 | 20 条 | 102 条 |

## 四、拆 Agent 的 3 个代价（和怎么省）

拆成 11 个 Agent 不是没有代价。以下是 3 个主要代价和我的处理方式。

### 代价 1：协调复杂度上升

11 个节点之间的状态传递、错误处理、超时控制，比 1 个 Agent 复杂得多。

**怎么省**：用 LangGraph 的 StateGraph 统一管理状态。每个 Agent 只关心自己的输入和输出，不感知其他 Agent 的存在。状态在 Graph 层面流转，Agent 本身保持简单。

### 代价 2：Token 消耗增加

每个 Agent 都需要自己的 Prompt（包含角色定义、约束、输出格式），总 Token 消耗比一个大 Prompt 多。

**怎么省**：Aggregator 用纯 Python，零 Token。RLS 权限注入在 SQL 层面，不经过 LLM。只有真正需要"理解"和"生成"的环节才用 LLM。

实测 V4 单次分析消耗 24,100 Token（输入 14,555 + 输出 9,545），单次成本 ¥0.03。比 V1 的一个大 Prompt 贵不了多少，但准确率和体验好得多。

### 代价 3：调试难度

11 个节点的链路，出了问题不好定位。

**怎么省**：每个 Agent 的输出都带 Metadata（调用耗时、Token 消耗、是否重试）。Reflection 质检 4 个维度（一致性/逻辑性/可操作性/完整性），问题报告会标注是哪个维度不达标。加上 192 条自动化测试覆盖核心链路，大部分问题能在测试阶段发现。

## 五、拆 Agent 的核心原则

如果你也在考虑"该不该拆 Agent"，以下是我在 EIA 项目中验证的 3 个判断标准：

**标准 1：上下文是否过载**

如果你的 Prompt 超过 2000 Token 的结构化数据（数据库 Schema、业务规则等），单个 Agent 的注意力会被分散。这时候拆分不是"过度设计"，是"必须的"。

**标准 2：是否需要并行**

如果你的场景需要查多个数据源（Sales + CRM + Finance），串行执行会让等待时间翻 N 倍。并行扇出能把 N 倍变成 1 倍。EIA 从 45 秒降到 15 秒，靠的就是这个。

**标准 3：故障是否需要隔离**

如果一个环节出错（比如 SQL 生成幻觉了字段名），你希望它影响整个流程还是只影响那一个 Agent？拆分后，故障被隔离在单个 Agent 内，其他 Agent 可以继续工作或提供降级方案。

**不建议拆的情况**：如果你的场景只需要查一个数据源、Prompt 不超过 1000 Token、响应时间要求不严格——一个 Agent 可能就够了。拆分有协调成本，不要为了拆而拆。

## 六、V1→V4 演进的商业逻辑

最后说一个容易被忽略的点：版本演进不是技术冲动，是商业瓶颈驱动。

| 版本 | 主题 | 商业逻辑 |
|------|------|---------|
| V1 | 能不能做 | 验证核心链路可行 |
| V2 | 好不好用 | 并行提速 → 用户愿意付费 |
| V3 | 爱不爱用 | 流式 + 交互打磨 → 续费率提升 |
| V4 | 企业级 | 多租户 → 可卖给连锁品牌总部 |

V1 推倒重构 V2 不是因为"架构不够优雅"，是因为 45 秒的响应时间让用户不愿意付费。V4 加多租户不是因为"技术先进"，是因为单租户版本卖不了连锁品牌总部。

每个版本解决一个商业瓶颈。技术决策服从商业逻辑。

## 写在最后

这篇文章的核心观点可以用一句话概括：

**一个超级 Prompt 解决不了的问题，不是 Prompt 不够好，是架构不对。**

3000 Token 的数据库结构会撑爆单 Agent 的注意力；一个节点出错，整个对话就废了；一个 Agent 的 Prompt 改起来，牵一发动全身。拆成 11 个分工明确的 Agent，响应时间从 45 秒降到 15 秒，故障被隔离，每个 Agent 的 Prompt 可独立迭代。

这不是"Multi-Agent 有多牛"的故事。是一个产品经理怎么用数据说服自己该拆、拆完付了什么代价、哪些代价可以省的决策复盘。
